# Architecture Guidelines

## Architecture Documentation Principles

- **Document decisions, not just designs** - Capture the "why" behind choices
- **Keep it current** - Outdated docs are worse than no docs
- **Appropriate detail** - Match documentation depth to audience needs
- **Visual first** - Use diagrams to communicate structure (Mermaid only, never ASCII art)
- **Executable where possible** - Encode architectural rules as fitness functions, not prose

## Architecture Decision Records (ADR)

### ADR Template

```markdown
# ADR-XXX: [Title]

## Status

[Proposed | Accepted | Deprecated | Superseded by ADR-XXX]

## Date

YYYY-MM-DD

## Context

What is the issue that we're seeing that is motivating this decision or change?

## Decision

What is the change that we're proposing and/or doing?

## Rationale

Why is this change being made? What alternatives were considered?

### Options Considered

1. **Option A**: [Description]
   - Pros: ...
   - Cons: ...

2. **Option B**: [Description]
   - Pros: ...
   - Cons: ...

## Consequences

What becomes easier or more difficult to do because of this change?

### Positive

- ...

### Negative

- ...

### Risks

- ...

## Architecture Characteristics Affected

Which NFRs this decision trades against (see "Architecture Characteristics" below).

## Verification

How compliance with this decision is checked (fitness function, lint rule, CI job, or
"manual review" if none exists yet).

## References

- [Link to related documentation]
- [Link to relevant discussions]
```

### ADR Examples

```markdown
# ADR-001: Use PostgreSQL as Primary Database

## Status

Accepted

## Date

2026-09-20

## Context

We need a reliable database for our application that supports:

- Complex queries and joins
- ACID transactions
- JSON data types for flexible schemas
- Good tooling and community support

## Decision

Use PostgreSQL 18 as our primary database, with UUIDv7 primary keys generated by the
native `uuidv7()` function and `TIMESTAMPTZ` for all timestamps.

## Rationale

### Options Considered

1. **PostgreSQL 18**
   - Pros: ACID compliant, excellent JSONB support, native `uuidv7()` for index-local
     primary keys, `MERGE`, row-level security for multi-tenancy, mature ecosystem, free
   - Cons: Requires more setup than managed document stores

2. **MySQL**
   - Pros: Popular, good performance, easy setup
   - Cons: Weaker JSON support, weaker constraint/extension story

3. **MongoDB**
   - Pros: Flexible schema, good for prototyping
   - Cons: Eventual consistency issues, not ideal for relational data

## Consequences

### Positive

- Strong data integrity guarantees
- Powerful query capabilities
- UUIDv7 keys keep B-tree inserts sequential (no UUIDv4 index fragmentation)
- Large talent pool familiar with PostgreSQL

### Negative

- Need to manage forward-only, expand/contract migrations
- DDL needs `lock_timeout` / `statement_timeout` guards for zero-downtime deploys

## Architecture Characteristics Affected

Data integrity (+), operational simplicity (-), write throughput (+ via UUIDv7)

## Verification

Integration tests run against a real PostgreSQL 18 container (Testcontainers), so a
divergence from the documented version fails CI.

## References

- [PostgreSQL Documentation](https://www.postgresql.org/docs/)
```

### ADR Lifecycle

ADRs are immutable once accepted. You never edit the decision of an accepted ADR - you
write a new one that supersedes it.

```mermaid
stateDiagram-v2
    [*] --> Proposed
    Proposed --> Accepted: Reviewed and agreed
    Proposed --> Rejected: Not pursued
    Accepted --> Deprecated: No longer relevant
    Accepted --> Superseded: Replaced by ADR-XXX
    Superseded --> [*]
    Deprecated --> [*]
    Rejected --> [*]
```

| Status                | Meaning                                      | Allowed edits              |
| --------------------- | -------------------------------------------- | -------------------------- |
| Proposed              | Under discussion, not binding                | Full edits during review   |
| Accepted              | Binding; code must comply                    | Status and References only |
| Rejected              | Considered and declined; kept for the record | Status and References only |
| Deprecated            | No longer relevant (feature removed)         | Status and References only |
| Superseded by ADR-XXX | Replaced; the new ADR links back             | Status and References only |

**Superseding rules**

- The new ADR's Context restates why the old decision no longer holds.
- The old ADR's Status becomes `Superseded by ADR-0042` with a link.
- Never delete an ADR. The record of a decision that was reversed is often more valuable
  than the decision itself.

**Where ADRs live**

```
docs/
└── architecture/
    ├── README.md               # System overview, links to C4 diagrams
    ├── characteristics.md      # Architecture characteristics / NFRs
    └── decisions/
        ├── README.md           # Index: number, title, status, date
        ├── 0001-use-postgresql.md
        ├── 0002-jwt-authentication.md
        ├── 0003-react-frontend.md
        └── 0004-docker-deployment.md
```

ADRs live in the repository, next to the code they govern, and are reviewed in the same
pull request as the change that implements them.

**When an ADR is required vs. a code comment**

| Situation                                                                       | Record as                   |
| ------------------------------------------------------------------------------- | --------------------------- |
| Choosing a database, framework, auth model, or deployment topology              | ADR                         |
| Anything hard or expensive to reverse                                           | ADR                         |
| A decision that constrains other teams or future work                           | ADR                         |
| Adopting or dropping a cross-cutting library (ORM, logger, test runner)         | ADR                         |
| A trade-off between architecture characteristics (e.g. consistency vs. latency) | ADR                         |
| Why one local algorithm was chosen over another                                 | Code comment                |
| A workaround for a known upstream bug, with issue link                          | Code comment                |
| Naming, formatting, file layout inside a module                                 | Lint rule or convention doc |

Rule of thumb: if a new engineer would ask "why is it like this?" six months from now and
the answer is not obvious from one file, it is an ADR.

## C4 Model

The C4 model gives four zoom levels. Use the first three routinely; the fourth (Code) is
generated on demand from the IDE rather than hand-maintained.

| Level        | Question it answers                                                 | Audience                          | Update cadence                          |
| ------------ | ------------------------------------------------------------------- | --------------------------------- | --------------------------------------- |
| 1. Context   | What is the system and who/what does it talk to?                    | Everyone, including non-technical | On new external integrations            |
| 2. Container | What are the deployable/runnable units and how do they communicate? | Developers, DevOps, architects    | On new service, datastore, or protocol  |
| 3. Component | What are the major building blocks inside one container?            | Developers on that container      | On significant internal restructuring   |
| 4. Code      | Class/type relationships                                            | Rarely documented                 | Generate on demand, never hand-maintain |

Keep one Context diagram per system, one Container diagram per system, and Component
diagrams only for containers complex enough to warrant them.

## Architecture Characteristics (NFRs)

Architecture characteristics are the "-ilities" the design is optimised for. Name them
explicitly, pick the few that drive the design, and state what you deliberately traded away.

| Characteristic          | How it is stated                    | How it is measured                            |
| ----------------------- | ----------------------------------- | --------------------------------------------- |
| Performance             | p95 API latency < 500ms             | OpenTelemetry histogram, load tests           |
| Scalability             | 2,500 req/s at 12 months            | Load test against projection                  |
| Availability            | 99.9% monthly SLO                   | Error-budget burn from SLI metrics            |
| Security                | OWASP Top 10:2025 controls in place | Automated scans, threat model review          |
| Accessibility           | WCAG 2.2 AA                         | axe in CI, manual keyboard/screen-reader pass |
| Frontend responsiveness | INP ≤ 200ms, LCP ≤ 2.5s, CLS ≤ 0.1  | Lighthouse CI, field RUM                      |
| Deployability           | < 15 min from merge to production   | Pipeline duration metric                      |
| Observability           | Every request traceable end to end  | Trace coverage of critical paths              |

Rules:

- Choose at most three to five **driving** characteristics. Everything cannot be first.
- Every ADR names the characteristics it improves and the ones it degrades.
- Each driving characteristic needs a measurable target and an owner, otherwise it is a wish.
- Record them in `docs/architecture/characteristics.md`; the `/nfr-capture` and `/nfr-review`
  skills read and maintain that file.

## Fitness Functions (Architecture Testing)

A fitness function is an automated test for an architectural characteristic. Prose rules
decay; executable rules do not. Run them in CI alongside unit tests.

### Layering and Dependency Rules

Enforce `Routes → Controllers → Services → Data Access` so that no inner layer reaches
outward and no module imports across feature boundaries.

```json
// .dependency-cruiser.json (excerpt)
{
  "forbidden": [
    {
      "name": "no-services-to-controllers",
      "severity": "error",
      "comment": "Services must not depend on the HTTP layer",
      "from": { "path": "^src/services" },
      "to": { "path": "^src/(controllers|routes)" }
    },
    {
      "name": "no-direct-db-from-controllers",
      "severity": "error",
      "comment": "Controllers go through services, never straight to data access",
      "from": { "path": "^src/controllers" },
      "to": { "path": "^src/db" }
    },
    {
      "name": "no-circular",
      "severity": "error",
      "from": {},
      "to": { "circular": true }
    }
  ]
}
```

The equivalent with ESLint 10 flat config and `eslint-plugin-boundaries` or
`import/no-restricted-paths` works just as well - pick one and keep it in the lint job.

### Other Fitness Functions Worth Having

| Rule                   | Tool                                        | Fails the build when                         |
| ---------------------- | ------------------------------------------- | -------------------------------------------- |
| Layering and no cycles | dependency-cruiser / ESLint boundaries      | An import crosses a forbidden edge           |
| Bundle budget          | Vite build + size check                     | Main chunk exceeds the documented budget     |
| API latency budget     | k6 / Artillery in CI                        | p95 exceeds the NFR target                   |
| Core Web Vitals        | Lighthouse CI                               | INP > 200ms, LCP > 2.5s, or CLS > 0.1        |
| Accessibility          | `@axe-core/playwright`                      | Any WCAG 2.2 AA violation                    |
| Supply chain           | `osv-scanner` / `npm audit`                 | New high/critical advisory                   |
| Contract stability     | OpenAPI 3.1 diff against the published spec | Undocumented breaking change                 |
| ADR compliance         | Custom check in CI                          | Code contradicts an accepted ADR (see below) |

### Automated ADR Compliance Checks

Give each enforceable ADR a machine-checkable assertion and link the check back to the ADR
number so a failure tells the engineer _which decision_ they broke:

- **ADR: PostgreSQL only** - a grep/lint rule fails on imports of another database driver.
- **ADR: parameterized SQL only** - lint rule bans template literals inside query calls.
- **ADR: Zod at every boundary** - a test enumerates registered routes and asserts each has
  a schema attached.
- **ADR: no direct `fetch` to third parties from the UI** - dependency rule restricting
  `src/features/**` to the internal API client.
- **ADR index freshness** - CI fails if `docs/architecture/decisions/README.md` does not list
  every ADR file with a current status.

Write the fitness function in the same PR as the ADR. An ADR with no verification path
should say so explicitly in its Verification section.

## Observability as an Architectural Concern

Observability is designed in, not bolted on. Decide instrumentation at the same time you
decide the component boundaries, because a boundary you cannot trace across is a boundary
you cannot operate.

**Baseline**

- **OpenTelemetry** for traces, metrics, and logs, exported over OTLP to a collector. The
  collector - not the application - decides where telemetry ends up, so backends can change
  without touching code.
- **Context propagation** via W3C `traceparent` across every hop: browser → API → worker →
  database. A request that loses its trace context at a boundary is an architecture defect.
- **Structured JSON logs** (`pino`) with redaction of secrets and PII, carrying `trace_id`
  and `span_id` so logs join traces automatically.
- **Semantic conventions** for span and attribute names, so dashboards survive refactors.
- **Health endpoints**: `/health` for liveness, `/health/ready` for readiness with real
  dependency checks.

**Architectural consequences to write down**

- Cardinality budget: which attributes may be high-cardinality, and which must not be.
- Sampling strategy: head vs. tail sampling, and what is always sampled (errors, slow paths).
- Cost: telemetry volume is a running cost; state the budget.
- Vendor neutrality: instrumentation is OTel; backends are replaceable.

```mermaid
flowchart LR
    SPA[React SPA] -->|traceparent| API[Express 5 API]
    API -->|traceparent| Worker[Background Worker]
    API --> DB[(PostgreSQL 18)]
    SPA --> Col[OTel Collector]
    API --> Col
    Worker --> Col
    Col --> Traces[Trace Backend]
    Col --> Metrics[Metrics Backend]
    Col --> Logs[Log Backend]
    Metrics --> SLO[SLO / Error Budget Alerts]
```

**SLO-based alerting**: alert on error-budget burn rate for user-facing SLIs (availability,
latency), not on raw CPU thresholds. Deploy automation rolls back on fast burn.

## Integration Patterns

### API Integration

```markdown
## [Service Name] Integration

### Overview

Purpose of this integration.

### Authentication

How we authenticate with this service (prefer OIDC/workload identity over long-lived keys).

### Endpoints Used

| Endpoint    | Method | Purpose        |
| ----------- | ------ | -------------- |
| /v1/charges | POST   | Create payment |
| /v1/refunds | POST   | Process refund |

### Error Handling

| Error Code | Meaning      | Our Response                                          |
| ---------- | ------------ | ----------------------------------------------------- |
| 400        | Bad request  | Log and surface a validation Problem Details response |
| 401        | Auth failed  | Alert, retry with new token                           |
| 429        | Rate limited | Honour `Retry-After`, exponential backoff with jitter |
| 500        | Server error | Retry 3 times with jitter, then fail loudly           |

### Idempotency

Unsafe POST calls send an `Idempotency-Key` so retries cannot double-charge.

### Rate Limits

- 100 requests/second
- Burst: 200 requests

### Circuit Breaker Settings

- Failure threshold: 5
- Recovery timeout: 30s

### Observability

Outbound calls are wrapped in a client span; failures and breaker state are metrics.
```

## Technical Debt Tracking

### Technical Debt Register

```markdown
# Technical Debt Register

| ID | Description | Impact | Effort | Priority | Owner |
|----|-------------|--------|--------|----------|-------|
| TD-001 | Legacy auth on an unmaintained library | High | Large | P1 | Team A |
| TD-002 | Routes without Zod validation | Medium | Small | P2 | Team B |
| TD-003 | Express 4 `asyncHandler` wrappers still in place | Low | Small | P3 | Any |
| TD-004 | Manual `useMemo`/`useCallback` predating React Compiler | Low | Medium | P3 | Any |

## TD-001: Legacy Authentication System

### Description
Auth uses an unmaintained token library with an open advisory, and secrets are verified
with a hand-rolled comparison.

### Impact
- Security risk (unpatched advisory; OWASP A07 Authentication Failures)
- Poor performance on token validation
- Difficult to add new auth methods (passkeys, SSO)

### Proposed Solution
Move verification to `jose`, shorten access tokens to 15 minutes, rotate refresh tokens in
httpOnly/Secure/SameSite cookies, and evaluate Better Auth / Auth.js for the surrounding
flows.

### Effort Estimate
2-3 sprints

### Dependencies
- Need to coordinate with mobile team
- Requires user session migration

### Acceptance Criteria
- [ ] All auth flows working with new system
- [ ] Zero downtime migration
- [ ] Token verification p95 improved by 50%
- [ ] Fitness function fails the build if the old library reappears
````

Track debt where the work is planned (issue tracker), and keep the register as the index.
Debt that has no owner and no priority is not tracked - it is remembered, badly.

### Capacity Planning

| ------------------------- | ------- | --------- | -------- |

| DB connections            | 50      | 100       | 50%      |

| Storage                   | 100GB   | 500GB     | 80%      |
| p95 latency               | 210ms   | 500ms     | 58%      |
| Error budget burned (30d) | 18%     | 100%      | 82%      |

## Growth Projections

| Timeframe | Users | Requests/sec | Storage |
| --------- | ----- | ------------ | ------- |
| Current   | 10K   | 500          | 100GB   |
| 6 months  | 25K   | 1,250        | 250GB   |

## Scaling Strategy

### Horizontal Scaling

- Add API server instances behind the load balancer
- Trigger: sustained p95 latency > 350ms or CPU > 70% for 5 minutes
- Scale down: CPU < 30% for 15 minutes

### Vertical Scaling

- Database: upgrade instance when connections > 80% or replication lag grows
- Cache: increase memory when eviction rate > 10%

### Connection Management

- Pool sized so that (instances x pool size) stays below the PostgreSQL connection limit
- Use a pooler (PgBouncer or the managed equivalent) before raising the server limit

### Data Sharding (Future)

- Shard by tenant ID when storage > 1TB
- Read replicas for reporting queries
- Row-level security already in place for multi-tenant isolation
